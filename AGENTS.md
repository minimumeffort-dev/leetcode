# Working in this repository

This is Horia's Python LeetCode practice repository. Keep each problem or standalone algorithm in its own descriptive file. Preserve useful alternate approaches in separate files.

## Coaching

- Match the help requested. Give a small hint when asked for a hint, and show code when asked for code.
- Explain concrete bugs and examples before rewriting a solution. A request for a review alone does not authorize replacing the user's implementation.
- Read the current file before editing. Preserve unrelated edits and the user's chosen approach unless a different approach is requested.
- Write plainly and briefly. Avoid hype, AI clichés, invented personal claims, and em dashes.

## Finished files and publishing

The user has authorized creating and maintaining the public GitHub repository at `https://github.com/minimumeffort-dev/leetcode`. They want every finished new file pushed and briefly explained in the README. This authorization also covers publishing verified improvements to existing practice files. Do not ask for another publishing confirmation within this scope.

When a solution is finished:

1. Run focused correctness checks appropriate to the change, including relevant edge cases. Syntax checks alone do not establish that an algorithm is finished.
2. Add or update its README entry with one short description of what the implementation actually does. Keep the user's direct, conversational tone. Describe alternate versions accurately.
3. Review the changes and stage only the finished file or files and their documentation. Leave unrelated edits and unfinished work unstaged.
4. Commit with a short descriptive message and push to `main` on `origin`. Confirm that the remote points to `minimumeffort-dev/leetcode` before pushing. Do not force-push or rewrite published history.
5. Verify that the push succeeded, then report the repository or commit link briefly.

During automated follow-ups, use this chat's completion context and focused checks to determine which changes are ready. Do not publish a file that is still being worked on, contains unfinished placeholders, or has unresolved correctness failures. If completion is unclear, leave it pending until the user finishes it or explicitly requests its review. Do not alter a draft just to make it publishable.

The README should explain every published Python file. Local caches, virtual environments, and private environment files do not belong in the public repository.
